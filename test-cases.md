# Тест-дизайн User Management API

## Контракт и допущения

- Базовый URL: `/api/users`. JSON использует camelCase.
- Тело POST/PUT содержит только `countryIsoCode` и `locale`. Неизвестные поля, в том числе `userId`, `dateCreated`, `dateModified`, отклоняются с 400.
- Страна: ровно две ASCII-буквы `[A-Za-z]`, без обрезки пробелов; сохранение через ToUpperInvariant. Справочник существующих стран не проверяется.
- Локаль: ровно `[a-z]{2}-[A-Z]{2}`, без нормализации и обрезки пробелов. Соответствие страны суффиксу локали не требуется.
- GUID в URL: любой формат, распознаваемый Guid.TryParse, кроме Guid.Empty. Непустой сегмент с неверным GUID → 400; отсутствие сегмента соответствует маршруту списка, а не ошибке GUID.
- Все даты формирует сервер в UTC. Создание: DateModified = null. PUT сохраняет UserId и DateCreated, устанавливает DateModified, даже если значения полей не изменились.
- GET/PUT неизвестного корректного GUID → 404. PUT не создает отсутствующую запись.
- Ошибки валидации возвращают JSON ValidationProblemDetails с непустыми описаниями; прочие ошибки — ProblemDetails без деталей исключения.
- Данные живут в пределах одного процесса. Перезапуск очищает память; несколько экземпляров сервиса имеют независимые хранилища. Параллельные PUT атомарно заменяют пару полей: сохраняется одна из целых версий.
- Каждый интеграционный тест (включая каждую строку Theory) получает новый WebApplicationFactory и новый singleton-репозиторий. Общего изменяемого fixture нет.

## Создание — POST /api/users

- [ ] POST с `RU` / `ru-RU` → 201, application/json, Location ведет на GET созданного пользователя.
- [ ] JSON содержит ровно пять свойств: userId (непустой GUID), countryIsoCode (строка), dateCreated (UTC ISO 8601), dateModified (null), locale (строка). Ответ десериализуется в User.
- [ ] DateCreated находится между серверными моментами до и после запроса; GUID сгенерирован сервером.
- [ ] Страны в нижнем, верхнем и смешанном регистре сохраняются в верхнем регистре; корректные локали сохраняются точно.
- [ ] Две одинаковые заявки создают две записи с разными GUID.
- [ ] Созданный пользователь доступен по Location и присутствует в списке.

## Чтение — GET /api/users и GET /api/users/{userId}

- [ ] Пустой репозиторий → 200 и JSON-массив `[]`.
- [ ] Список нескольких пользователей → 200; все созданные записи без пропусков/дубликатов, корректная схема каждого объекта; порядок не фиксирован.
- [ ] GET существующего пользователя → 200, все значения совпадают с сохраненными; чтение не изменяет даты.
- [ ] GET неизвестного непустого GUID → 404 и понятный ProblemDetails.
- [ ] GET с GUID в разных допустимых форматах/регистрах возвращает ту же запись.

## Обновление — PUT /api/users/{userId}

- [ ] PUT существующего пользователя → 200, обновленные CountryIsoCode и Locale; страна нормализована.
- [ ] Ответ содержит полную схему пользователя; UserId и DateCreated сохранены; DateModified — UTC-время обновления.
- [ ] Повторный GET и GET списка возвращают именно обновленные данные; количество записей не меняется.
- [ ] Повторный PUT с теми же данными успешен и выставляет DateModified.
- [ ] Обновление одной записи не меняет соседнюю.
- [ ] PUT неизвестного корректного GUID → 404; запись не добавлена.

## GUID — параметризованные негативные проверки для GET и PUT

- [ ] `not-a-guid`, GUID неверной длины, GUID с не-hex символами, число, пробел → 400.
- [ ] `00000000-0000-0000-0000-000000000000` и эквивалентный формат без дефисов → 400.
- [ ] Ошибка содержит userId и понятное непустое описание; неверный PUT не изменяет хранилище.

## CountryIsoCode — Theory/InlineData для POST и PUT

- [ ] null, пустая строка, пробелы, пропущенное поле → 400 с ошибкой CountryIsoCode.
- [ ] Одна/три буквы (`R`, `RUS`), цифры (`12`, `R1`), спецсимволы (`R!`, `--`) → 400.
- [ ] Кириллица (`РУ`), Unicode-буквы вне ASCII (`ÜS`) → 400.
- [ ] Пробелы по краям (` RU`, `RU `), конечный перевод строки → 400.
- [ ] Невалидное поле не создает запись и не меняет существующую запись, в том числе DateModified.

## Locale — Theory/InlineData для POST и PUT

- [ ] null, пустая строка, пробелы, пропущенное поле → 400 с ошибкой Locale.
- [ ] Неверная длина (`r-RU`, `rus-RU`, `ru-R`, `ru-RUS`) → 400.
- [ ] Неверный регистр (`RU-ru`, `RU-RU`, `ru-ru`, `Ru-RU`) → 400.
- [ ] Неверный разделитель / отсутствие дефиса (`ru_RU`, `ruRU`), цифры (`12-34`), спецсимволы (`r!-R!`) → 400.
- [ ] Кириллица (`ру-РУ`), пробелы по краям, конечный перевод строки → 400.
- [ ] Невалидное поле не создает запись и не меняет существующую запись, в том числе DateModified.
- [ ] Два невалидных поля возвращают обе ошибки в одном ответе.

## Тело запроса и протокол — POST и PUT

- [ ] Отсутствующее тело, JSON `null`, `{}`, поврежденный JSON, корневой массив/строка/число → 400 без изменения состояния.
- [ ] Число/массив/объект вместо строкового поля → 400.
- [ ] Попытка передать userId/dateCreated/dateModified или произвольное лишнее поле → 400; серверные поля не подменены.
- [ ] Неподдерживаемый Content-Type (`text/plain`) → 415.
- [ ] Неподдерживаемый DELETE для существующего маршрута → 405.
- [ ] Неизвестный маршрут → 404.
- [ ] После некорректного запроса API продолжает принимать валидные запросы.

## End-to-End

- [ ] POST → GET по Location → PUT → повторный GET → GET списка. Проверить коды, типы JSON и значения на каждом шаге, неизменность идентификатора/даты создания, появление DateModified и отсутствие дубликатов.

## Потокобезопасность и устойчивость

- [ ] Параллельные POST: все ответы 201, GUID уникальны, число записей равно числу успешных запросов, данные не потеряны.
- [ ] Параллельные PUT одной записи с разными парами полей: все ответы 200; каждый ответ/GET содержит целую пару, DateCreated и UserId сохранены, итоговая запись соответствует одной из заявок.
- [ ] Одновременные POST/PUT/GET списка: нет 500, исключений перечисления и частично обновленных объектов; итоговые данные полны.
- [ ] После серии параллельных и ошибочных запросов обычный POST/GET/PUT продолжает работать.
- [ ] Неожиданная ошибка репозитория → 500 ProblemDetails без stack trace; следующий исправный запрос успешен.
- [ ] Два независимых WebApplicationFactory: пользователь первого отсутствует во втором; второй список пуст.
- [ ] Каждый новый тест начинает с пустого репозитория; нет зависимости от порядка тестов или отключения параллельности xUnit.

## Репозиторий (дополнительные модульные проверки)

- [ ] Add возвращает добавленного пользователя; GetById/GetAll возвращают сохраненные данные.
- [ ] Повторный Add с тем же GUID не перезаписывает запись (явная ошибка).
- [ ] Update существующего GUID → true, неизвестного → false без вставки; GetById неизвестного → null.
- [ ] Объекты User неизменяемы после создания; GetAll возвращает снимок, безопасный при последующих записях.
